# Decompiling NFS4.EXE to Rust

The game runs as the original's code statically recompiled from MIPS (`crates/nfs4rc`): exact,
but machine code in Rust syntax. `crates/nfs4` replaces it function by function with readable
Rust, checked against the recompiled original as it goes. The race logic, the AI and the front
end were first ported bit-exact (the original's stack and registers too); since 2026-11-02 the
goal is readable Rust that no longer needs `ps1rt` at all (see "The plan").

## The plan

Decided 2026-11-02: no more bit-exact ports. What isn't decompiled yet is written readable
from the start, the bit-exact ports are rewritten readable, and then the game leaves the PS1
runtime subsystem by subsystem.

**The rule: the game's state stays exact, the rest is free.** A port keeps the original's
writes to the game's data (and their order where data can overlap) but not its stack layout,
its registers' leftovers or its code's shape. The recompiled original stays the reference:
fuzz tests and `decomp-check` lockstep runs compare against it, and they only work while the
state matches. Deliberate changes to the game's behaviour come after a subsystem is native,
as their own commits. Where the original's output only reaches the host (pictures, sound),
the checks compare that instead (`tools/tourshots.py`, the primitives drawn).

1. **Finish the readable front end** (see "The readable front end"): the rest of the screens,
   FRONT, FEMENUDEFS and the other bit-exact front-end ports. Done 2026-11-02.
2. **The race's leftovers.** Run the race in lockstep with `NFSHS_DECOMP_SCRAMBLE=race` to find
   every place the race's bit-exact code reads stack or register leftovers (the barrier
   check's uninitialized wall normal is one), and make those values explicit, before readable
   code changes the stack under them. Done 2026-11-03: see "The race's leftovers".
3. **The rest of the game, readable from the start:** the HUD, the camera, the pause menu, the
   replays, then the drawing (DRAW*, RENDER, R3DCAR, TRACK, OBJECT, FLARE, WEATHER, NIGHT,
   TEXTURE*, HRZSKU, SKIDMARK, TRSPROJ) and the sound and speech (SPEECH, SPCHEVNT, AUDIO*,
   COPSPEAK, TRGSFX). The drawing is checked by pictures and the primitives it emits. The HUD
   (HUD.CPP, all 62), the camera (CAMERA.CPP, all 41) and the pause menu (MPAUSE.CPP,
   PAUSEMENU.CPP, RPAUSE.CPP, all 73) done 2026-11-03, the replays (REPLAY.CPP, all 16)
   2026-11-07: see "The readable HUD". The drawing started 2026-11-07 with the files the host
   doesn't draw for itself: the tyre marks (SKIDMARK.CPP, all 11), the GTE's set-up
   (TRSPROJ.CPP, all 11), the fog and depth cue (TEXTUREPROCESS.CPP, all 16), night driving
   (NIGHT.CPP, all 19) and the rain and snow (WEATHER.CPP, all 25); then the textures into VRAM
   (TEXTURE.CPP, all 24), the first of the files the host hooks or names; then the sky and the
   horizon (HRZSKU.CPP, all 22).
4. **The bit-exact ports rewritten readable:** physics, Newton, collisions, the race logic and
   the AI (what the planned changes touch first).
5. **Off `ps1rt`, a subsystem at a time**, once nothing recompiled reads its data: typed RAM
   views become native structs, the files loaded with PS1 pointers inside (shapes, tracks)
   are parsed into Rust types, the GTE's arithmetic becomes native integer code giving the
   same results, primitives become calls into the renderer, and the SPU, CD, pads and memory
   card become the host's. The front end can go first: it is all decompiled.

## How it fits together

- **State stays in PS1 RAM.** The code still recompiled reads the cars and globals there, so
  the decompiled code works on them in place, through typed views:
  `car.n().linear_vel().update_x(&mut c.m, |v| ...)`. A view (`types::Car(addr)`) is the
  address of a structure; its accessors read and write RAM. Native Rust state comes once
  everything that touches a structure is decompiled.
- **`crates/nfs4/src/types.rs`** is generated by `tools/gentypes.py` from the development
  build's layouts (`re/nfs4_types.h`, from `NFS4.SYM`): a view per structure in `ROOTS` and
  what they hold, a getter, setter and `update_` per field, and a field table for naming
  addresses. Add a structure to `ROOTS` and run `python gentypes.py` (in `tools/`).
- **Globals** are in `crates/nfs4/src/globals.rs` at their retail addresses. `tools/globmatch.py`
  carries the development build's global names over to retail (`re/retail_globals.tsv`:
  address, name, development address, how it was matched, votes, type). It works from
  `re/retail_syms.tsv` (the function matches of `tools/symmatch.py`).
- **Modules are the original's source files**: PHYSICS.CPP is `physics.rs`, MATHNFS.CPP
  `mathnfs.rs`, and so on. `fixed.rs` holds the EA fixed-point library (`fixedmult`,
  `fixeddiv`...) and the R3000's `div`.
- **Routing.** `tools/decomp_funcs.txt` lists the functions decompiled. For calls to them,
  `tools/recomp.py` emits `if !(c.decomp)(c, ADDR) { f_ADDR(c); }`, and `nfs4::install` makes
  `Cpu::decomp` (and calls by address) run the Rust version. The recompiled originals stay
  generated: they are the fallback and the reference. Regenerate `crates/nfs4rc` (in `tools/`:
  `python recomp.py ../crates/nfs4rc/src --all`) after changing the list. Listing a
  function that is not decompiled yet is harmless, because the hook declines it.
- **Each function** is registered in `nfs4::FUNCS` with an ABI entry (`abi_*`), which reads
  a0..a3 and the stack arguments and writes v0. Decompiled code calls other decompiled code
  as plain Rust, and calls code still recompiled with `abi::call(c, nfs4rc::f_XXXXXXXX,
  &[args])` from inside an `abi::frame`.
- **The original's stack layout.** A function that calls recompiled code or passes a local
  by address runs in `abi::frame(c, SIZE, |c, sp| ...)` with the original's frame size (its
  `addiu sp, sp, -SIZE`), and keeps those locals at the original's offsets from `sp`. The
  original reads stack it never wrote: `Physics_DoBarrierCheck` turns the car with a wall
  normal it only sets on one path, so on the other it gets whatever an earlier call left
  there. The decompiled code has to read and leave things where the original's would be.
  Likewise a callee that homes its register arguments (`sw a2, 48(sp)` into the caller's
  frame) writes them there too. In a race the stack is in the scratchpad (around
  0x1F8002AC..0x1F8003DC for the physics), and the original's frames nearly fill it.
- **Saved registers.** The original's prologues save the caller's s-registers and the return
  address in their frames, and those leftovers are read too: `TrgSfx_AddSkidmark` builds a
  skid mark's colour on the stack without its fourth byte, which then comes from
  `Physics_CorrectPostCollisionYaw`'s saved return address. The ports keep no registers, so
  `nfs4::decomp` replays the original's prologue stores (read from the EXE) on every call from
  recompiled code, whose registers hold what the original's would. Where a port calls a
  decompiled function and the leftovers matter, it does the same with `abi::leave_prologue`,
  giving the s-registers and return address the original caller would have; a recompiled
  callee gets them with `abi::call_from`. A port that calls out a lot keeps an `abi::Saved`, the
  original's s-registers and fp as it sets them, and calls through it (`Saved::call`, `Saved::enter`, `Saved::call_ptr` for the original's calls
  through function pointers, and `Saved::call_leaving`, which leaves the callee's scratch
  registers: a variadic `sprintf` homes a2 and a3 whatever they hold, so a call that passes
  fewer arguments takes them from the calls before). `physics::tests::barrier_stack_fuzz` compares the
  whole scratchpad stack after the barrier test.
  A port leaves its frame as the original's when it returns: its locals at the original's
  offsets, its callees' frames below (the library's too: `intatan` is called recompiled for its
  frame, `crossproduct`'s prologue left with `Saved::enter`), each entered with the original's
  registers and return address.
- **Checking the stack**: `test_util::same_stack` enters a port from recompiled code on a
  stack filled with a random byte (the scratchpad, or main RAM for calls that nest deeper than
  the scratchpad holds) and compares every stack word and the RAM with the original's.
  `STACK_WHO=1` names, for each differing word, the routed function whose frame last held it
  and the offset in it (a saved register, a local, a callee's homed argument). It knows only
  routed calls: a word last written by a callee still recompiled is put down to the routed
  frame around it, so when a "local" makes no sense, look for a callee whose prologue saves a
  register there (a temporary write watch on the word in `ps1rt::Mem::w32` finds it; the
  backtrace's function names are unreliable in release builds).
- **Host hooks**: the host intercepts some of the game's functions (`tools/hook_funcs.txt`, its
  match arms in `src/ps1/host/`): the showroom's car is noted at `DrawCar`, the sliders', halos'
  and video walls' primitives are captured, the autosave runs before a front-end frame's
  `Redraw`. A port calls these by address (`Saved::call_ptr`, `call_ptr_leaving`): `Cpu::call`
  runs the host first, then routes to the port if there is one. Calling the port (`port()`,
  `Saved::enter`, an `*_entry` fn) or `nfs4rc::f_*` directly skips the host; only the picture
  changes (every car shown as the first one, the sliders gone, no autosave), which RAM checks
  don't see. `python tools/hookaudit.py` lists such calls. The host also reads `Cpu::stack` to
  know what the game is doing (a save it started is `GenericMenuSaveGame` on it): the routing
  and `Saved::enter*` push a port's address there as the original does (`abi::on_stack`).

## Porting a function

1. Read it. The recompiled body in `crates/nfs4rc` has each MIPS instruction as a comment.
   `python fdis.py ADDR` (in `tools/`) disassembles it more compactly. Its name and source
   line are in `re/retail_syms.tsv` / `re/nfs4_funcs.tsv`, and its argument and structure
   types in `re/nfs4_types.h`.
2. Write it in the module of its source file under its original name in snake_case, with a
   doc line `` `Original_Name` (FILE.CPP, 0xADDRESS): what it does ``.
3. Keep the original's arithmetic: wrapping operations where it can overflow, `x / 256` for
   its round-toward-zero shifts (`(x + 255) >> 8` when negative), `>>` where it shifts
   (rounding down), `fixedmult` for each product it rounds, and `fixed::div` for its `div`. Read
   bytes as the original does (`lbu`: `as u8`). The original's dead results can go (a pure
   call whose value is unused), but its writes to RAM must all happen.
4. Register it in `FUNCS` (sorted by address) and add it to `tools/decomp_funcs.txt` if it
   isn't there.
5. Check it (below) until it matches. Commit one function or a small group at a time.

## The readable front end

The front end is rewritten as readable Rust (decided 2026-11-01, done 2026-11-02; step 1 of "The plan"), module by module:
the game's data in RAM stays exactly the original's, but the stack and the registers no longer
reproduce the original's layout and leftovers. `NFSHS_DECOMP_SCRAMBLE=1` (below) measured what
that costs: nothing the game does depends on them but three places, now handled (the controller
screen's label buffer, the save's unfilled bytes, which load the same, and the host's autosave
sounds, now found through `tDialog::Display`/`Hide`'s hooks).

- Objects are typed views (`crate::types`); a derived class's view reaches its base class's
  members, `base()` is its base class's view.
- Calls into the game go through `crate::call`: `call(c, f, args)` for a function,
  `call_addr` for a hooked function or a pointer, `call_virtual(c, obj, vptr, slot, args)` for a
  virtual one, `with_buffer` for stack space the game's code takes by address. No frames of the
  original's size, no saved registers, no return addresses: `crate::abi` stays for the code not
  rewritten yet (and the race's, which keeps its fidelity).
- A rewritten module keeps the original's writes to the game's RAM and their order where data
  can overlap (the fuzz tests place objects anywhere); reads that nothing in between can change
  may be merged.
- Checks: its fuzz tests (`against_original`: RAM but the dead stack, the result, the random
  state), `decomp-check --main` with and without `NFSHS_DECOMP_SCRAMBLE=1`, `tools/tourshots.py`
  (pictures; cards that differ must load the same) and `tools/hookaudit.py`. The front end's
  stack tests are gone: they checked the fidelity this drops.

Rewritten so far: FEMENU.CPP, FEMENUEXTENDED.CPP, FEMENUOPTIONS.CPP, FETEXTRENDER.CPP, FEDIALOG.CPP,
FEAPP.CPP, FESCREEN.CPP, SCREENDISPLAY.CPP, SCREENTROPHYINFO.CPP, SCREENTRACKINFO.CPP,
SCREENUSERNAME.CPP, SCREENAUDIO.CPP, SCREENTRACKRECORDS.CPP, SCREENTROPHYROOM.CPP,
SCREENTRACKS.CPP, SCREENTOURNSELECT.CPP, SCREENPINKSLIPS.CPP, SCREENPOST.CPP, SCREENMAIN.CPP,
FEFADES.CPP, FELINES.CPP, FETV.CPP, DRAWSHP.CPP, FETEXTURE.CPP, FEMISSION.CPP, MMEFFECT.CPP,
MINFRONT.CPP, MOVIE.CPP, FETOOLS.CPP, FEINPUT.CPP, FECHEATS.CPP, FETRACKS.CPP, STATTOOL.CPP,
STATCHK.CPP, FEVIDEOWALL.CPP, FECREDITS.CPP, FECARS.CPP, FETOURN.CPP, FE3DMENU.CPP, FEAUDIO.CPP,
SCREENCONGRATS.CPP, PSXFRONT.CPP, MEMCARD.C, FEMEMCARD.CPP, SCREENMEMCARD.CPP,
SCREENCONTROLLER.CPP, FRONT.CPP, SCREENCARSELECT.CPP, FEMENUDEFS.CPP: the whole front end (step 1
done).

The fuzz tests' RAM comparison leaves out the whole main stack (to 0x80200000, as
`decomp-check`): the original homes its arguments in its caller's frame, which the rewritten
code doesn't. Buffers a rewritten port copies texts into are larger than the original's, whose
overruns stayed in its own deep frame.

Where an old port passed a virtual call only its object, the original relied on its own
arguments still being in a1..a3 (`tInsideBoxMenu::ProcessInput` passes its first item the
player, key and command that way). The scramble experiment kept registers a port set or
didn't touch, so it didn't test those: a rewrite passes them as arguments.

Two of the game's values hang on the stack's layout, and so differ now: the pink slips' second-card
message is printed on `MainLoop`'s stack and its address kept in the no-input dialog (`gFEApp + 864`),
and `RunPostGame` reads the record lap's car (`StatChk_IsRecordLapTime`'s `*car`, written only when a
car is checked) from whatever its stack holds otherwise; the rewrite starts it at 0.
The car select's marks (`tScreenCarSelect::DrawOverlay`, overlay kinds 4 and 5) test bits of a car
`GetCar` may not have filled in (an empty garage): the original then reads the stack's leftover,
the last `y` `DrawShapeExtended` homed while FESCREEN drew the background strips. The rewritten
FESCREEN leaves something else there, so which marks light up on such a screen may differ; the
car select's fuzz test keeps out of that state. The same goes for its video wall with no car: the
original gives the wall the `fAvailable` of the car it didn't get, and `UpdateVideoWall` notes its
livery (the stack's leftover, or in the duel the opponent's car read into the same buffer before).
The rewrite clears its car buffers when it makes them, and keeps the duel's reuse.

The test CPUs' `systemtask` lets a tick go by (the word `timedwait` reads), so code that waits
(`Front_ResetPSXController`, the memory card's checks) runs in the tests; their `GetDirentry`
fills the card's directory from `test_util::DIRECTORY` when it's marked.

The test CPUs stand in for the host's shape emitter (0x8004e74c, under `DrawShapeExtended`): in
the game the host draws the shape and the original never runs, and the original reads stack it
never wrote. Instead of running it, the test CPU logs what the host would get (shape, flags,
position, the four colours, blending) at `test_util::SHAPES_EMITTED`, which the tests compare.

The menus' key and command names follow the pad and `MainLoop`'s jump table (0x80010070): key 16 is
back (Triangle) and 8192 start (Start); commands 1 to 8 are go to, go to with the back stack emptied,
go to with the second player's menu, back, race, race when both players are ready, race, quit.
`tMenu`'s vtable slot 56 is `TransitionIsFinished` and 64 `IsSubMenu` (the old FEAPP port had them as
"in transition" and "transition is finished").

## The race's leftovers

Step 2 (2026-11-03) ran races in lockstep with `NFSHS_DECOMP_SCRAMBLE=race`, which junks the
race's ports' leftovers (every port outside the front end, the scratchpad stack included), with
`NFSHS_DECOMP_RESYNC=1` so one run lists every difference: the reference race (track 0, one
lap, `BOOT_SCRIPT="8:-,150:x"`), tracks 2 to 6 with rain, night and traffic, a reversed track, a
police car as the player (`GS_SET=3d4=27`), the pause menu's restart, and the eight front-end
tours. Every AI module and the rest of the race logic read none. What reads leftovers:

- **The barrier check's wall normal** (`Physics_DoBarrierCheck`, from `Collide_CheckMeForCollisions`):
  a car on its wheels scraping a barrier is turned with a normal that is only set on the
  bounce path; on this one it is whatever is at scratchpad 0x1F8002CC, a slot written about
  60,000 times a race by dozens of functions (`NFSHS_WATCH` showed `Newton_TestForUndrivableSurfaces`'
  last wheel point, its sp+80, in 4 of the 7 reads seen, and `Newton_ApplyTheLawOfGravity`'s
  locals in the other 3). It is a world position, not a unit vector: the car gets a yaw kick.
  0 to 5 reads a race. It can't be modelled as a value: exactness would mean keeping the
  original's stack layout for every function at that depth. Decided (the user, 2026-11-03):
  the bit-exact ports stay as they are for now (exact), and when the physics is rewritten
  readable (step 4) it is fixed as a bug, with a real normal (the barrier's, as the bounce
  path uses), and documented; lockstep checks resync over those frames.
- **The skid marks' colours** (`TrgSfx_AddSkidmark`, still recompiled): built on its stack
  without the top byte, which comes from whatever the stack held (a saved return address).
  Stored in `gPrevSkidSm` and the marks' segments (gp+5484); the host draws the marks with the
  low 24 bits, so `decomp-check` ignores a difference in that byte alone there.
- **The car's drawing** (`0x800b0868` after `R3DCar_MATRIX3DT_Copy`, still recompiled): one
  word of its per-frame transformed vectors (seen at 0x801c978c in a rain, night and traffic
  race) comes from its stack (a saved return address in the original). Pictures with and
  without the scramble are the same; it gets a defined value when R3DCAR is decompiled.
- **The libraries' saved registers**: `InitGeom` keeps its return address at 0x80135d60 while it
  runs, `_patch_gte` and the timer's set-up keep stack pointers at 0x80053684 and 0x8014e2bc;
  nothing reads them after. A readable caller has another stack depth, so `decomp-check`
  ignores those three words (they made the front-end tour differ from the PSXFRONT rewrite on).

Tools: `NFSHS_DECOMP_SCRAMBLE=race` (or `all`; `1` the front end), `NFSHS_DECOMP_SCRAMBLE_ONLY=Name,...`
to bisect by function, `NFSHS_DECOMP_RESYNC=1` (report, give the decompiled run the original's
words, go on), `NFSHS_WATCH=addr` (which code changes a stack slot, between port entries,
exits and calls). Track 1 doesn't boot headless (`Track_Init` spins in the watchdog), with or
without the decompiled code.

## The readable HUD

HUD.CPP (`crates/nfs4/src/hud.rs`) was written readable from the start, without a bit-exact
pass first: each function read from its disassembly, written in the front end's readable style
(state exact, the stack and registers free), fuzzed against the recompiled original on the race
RAM (`hud_fuzz`) with planted mutants, and checked by the tours in lockstep and their screenshots.
`gpu.rs` holds the primitive set-up (`addPrim`, `SetPolyF4`...) the HUD inlines.

- **The host's hooks.** The host draws the HUD's text, boxes and pause box itself and records the
  rest (`Hud_BuildString`, `Hud_FBuildF4`, `Hud_BlackThinBox`, `Hud_RenderPauseBox`,
  `Font_TextXY`, `Flare_2DHalo`): ports call them by address (`call_addr`). The host skips
  recording what the functions it draws itself (`RenderMapView`, `Draw321Num`, `Render321Go`,
  `BigBTCTime`, `RenderHudView`, `RenderTacView`) call, telling them by the innermost function
  on the call stack: so those ports call every sub-function through `call`/`call_addr` (each
  pushes itself), never as plain Rust, or the host would take a sub-function's calls for theirs.
- **The original's quirks kept.** The radar's quarter-scale pass reads the police not in the
  world at places it never worked out (the stack's leftovers): only a "far" result can come of
  it, which the map treats as none, and the places stay at the original's stack offsets so the
  fuzz sees the same leftovers. The busted overlay clears a perp's record before copying its
  name in, quitting copies first (a long name runs into the record's time).
- **Testing views.** The views' functions draw into a view's primitive buffer, which
  `Draw_StartRenderingView` ends at `Draw_gMaxPrim`; `Flare_2DHalo` only draws with 4 KB to
  spare, so the fuzz points both ends past its free RAM (else the halos' sizes go untested).
- **Reading the disassembly.** `tools/fdis.py` leaves out delay-slot `nop`s: an instruction that
  looks like it sits between a call and the next is after the call (`Hud_PositionMap`'s second
  load of the map's turn is `csin`'s argument, not a leftover of `ccos`'s).

- **The camera (CAMERA.CPP, `camera.rs`).** Written the same way. Its bits word (`camera_info`
  +0x74) holds the mode's flags with two byte counters in it (the transition's, +0x75, and the
  crash's, +0x76): the ports keep the original's order of byte and word writes to it. The tail
  and helicopter cameras are one chase routine with each's constants. The fuzz cases need the
  camera in a tunnel (a slice's acoustics), far from its car, off the road and mirrored to
  reach every branch; an animated camera that has finished is only reached by the tours.

- **The pause menu (MPAUSE.CPP, PAUSEMENU.CPP, RPAUSE.CPP: `mpause.rs`, `pausemenu.rs`,
  `rpause.rs`).** PAUSEMENU.CPP is a smaller copy of the front end's menu classes (its items'
  vtable pointer at +8, the menu's at +80; a title as item 0, `fNumItems` not counting it);
  the menus are made once a race (`tPauseMenuDefs`, at 0x801529f8 in the race RAM, which the
  fuzz uses as the game left it). `tPMenu`'s constructor is variadic: from the game it homes
  a1..a3 in its caller's argument area and reads the items on from there, as the original
  does; `CheckForDisabled` and up and down loop for ever on a menu with nothing to go to, so
  the fuzz keeps one item usable. The slider divides by its maximum (never 0 in the game: the
  original traps), and draws its arrows once for each of its 15 bars. `MPause_MusicLogic`'s
  sound options buffer is the library's to fill (the test CPUs don't), which changes no RAM.
  The test CPUs answer `PadGetState` from `test_util::PAD_STATE`, for the vibration items.

- **The replays (REPLAY.CPP, `replay.rs`).** A replay is the humans' pads, recorded a tick at a
  time into 32-tick records (`controlData`: 32 steering bytes, then the gases, brakes and
  flags, each a part) and each full record run-length coded into the replay buffer, four parts
  of at most 33 bytes; watching, the records are read back and drive the cars, under the
  track's TV cameras (`camera.viv`, chosen by the slice the car is on). The coding doesn't escape
  a lone 0xFF byte, which the reading then takes for a run (the original's bug, kept; only the
  flags byte can be 0xFF). The reading copies each part into a buffer in its frame and decodes
  it there, so such a part, ending in a mistaken run, reads the buffer past its end: the port
  keeps the buffer across a record's parts as the original does, and starts it zeroed where
  the original has the stack's leftovers. Every race tour records (each tick's `SaveInput`, a
  record coded every 32); none watches a replay (the game shows one only after a finished race),
  so playing back, the replay's controls and the TV cameras' cuts are checked by the fuzz alone
  (`replay_fuzz`: coded records to read, the track's cameras and other modes). The test CPUs
  find no files, and the recompiled `LoadCameraFile` calls `loadfileadrz` directly, so
  `replay_camera_file_fuzz` enters the original after that call (`f_800b61d4_at`, its frame and
  v0 set up) with a camera file in RAM, against the port's `install_cameras`.
  A trap found here (see "The spin-tick trap" below): clearing the buffer at the race's load is
  a 24,576-pass loop in the original, and a port clearing it without ticking left the race's
  clock a tick behind (found by the lockstep tours, not the pictures).

- **The drawing: the tyre marks (SKIDMARK.CPP, `skidmark.rs`) and the GTE's set-up (TRSPROJ.CPP,
  `trsproj.rs`).** The host draws the marks itself from their chunks in RAM (`read_skids`), so
  the ports keep the chunks exact; `Skidmark_OnyxBuildFacets` hands the race's own drawing
  (`Draw_kCtrlSkidmark`, still recompiled) the view's turn and the chunks. Its fuzz draws for
  real: the scratchpad's ordering table and primitive pointers at free RAM (as the HUD's), the
  race's camera view (`gCView`) and the chunks moved in front of it (the race RAM's marks are
  behind the camera), keeping to the chunks and segments the race filled (others hold junk
  links the original follows off the scratchpad). TRSPROJ is the first port to drive the GTE
  itself (`Cpu::gte_write`, `gte_command`, `gte_read`): its results are GTE registers, which the
  fuzz compares by loading the GTE from RAM before each run and writing its registers back to
  RAM after, as code reads them. The original packs the matrix's last element and the vector's
  z from 32-bit stack words whose top halves are leftovers; the GTE uses only the low halves, so
  the ports write the shorts alone.

- **The fog and depth cue (TEXTUREPROCESS.CPP, `textureprocess.rs`) and night driving (NIGHT.CPP,
  `night.rs`).** The depth cue's palettes go to VRAM through the host's `LoadImage`, which the
  RAM comparisons can't see: the test CPUs' stand-in hashes each upload's rectangle and pixels
  into `test_util::LOADED_IMAGES`. The fog files and `night.psh` aren't on the test CPUs, so
  `fog_file_fuzz` enters `Fog_ReadFogKeys` after its load (as the camera file's test does) and
  the night's set-up is fuzzed on its other paths; the night races below run the rest. The
  fog's keys are a ring the search walks for ever if it has one key, so the fuzz builds rings of
  two or more (the game never searches a ring of one). Night's light tables are built on the
  scratchpad (`gTableCache`) and copied back to the world's 256 colour places, past the world's
  own. `Night_CreateNightTableElement` reads the nearest colour's index from its frame, which
  the search leaves unset only when no colour is nearer than 3 x 255 squared; the port starts it
  at 0. `Night_SetCopColor` indexes a two-word table in its frame by a byte the game's table
  keeps to 0 or 1 (the port masks it).

- **The rain and snow (WEATHER.CPP, `weather.rs`).** The host calls `Weather_BuildWeather` itself
  for each view it draws and records the primitives it adds (the host's `views.rs`), so the
  port's primitives are what the screen shows; they are in RAM, so the rain races check them in
  lockstep. The fuzz builds a weather state on the race RAM (a dry day's): the particles' blocks,
  rain's or snow's box, particles in it and just past each side, the lens's drops, the levels,
  the race's camera view turned and moved a little since the last frame, the GTE loaded and
  dumped as for TRSPROJ. The original packs its vectors' z with stack leftovers in the top half,
  which the GTE never reads. `Weather_TransformVertex` loops on and on given no particles (the
  game never does).

- **The textures (TEXTURE.CPP, `texture.rs`).** The host only names its functions (its own
  readers follow the same formats), so the port is checked like the others: the fuzz builds a
  shape (an image block of any depth and size, flipped or not, its palette, a translucency
  record) and the loading's state (palettes shared, one now and then the shape's own; the free
  CLUT lists short or empty; kept car palettes), and compares RAM, ticks (all of it runs while
  the game loads) and what `LoadImage` was given. A loop's match can be a backward branch too:
  `Texture_CheckForSharedPalette` ticks once more on a match of 256 colours and twice on one of
  16. The front end's ports that called `Texture_GetClutId`, `Texture_MenuReleaseClutId` and
  the menu textures' set-up through their originals call them by `call_jal` now.

- **The sky and the horizon (HRZSKU.CPP, `hrzsku.rs`).** The host draws the sky itself from what
  the set-up leaves (`SkyData` in `src/ps1/race.rs`) and calls only `HrzSetPsxMatrix`, so the
  building functions (`Hrz_BuildHorizon`, `Hrz_BuildSky`, the stars, the lightning's forks) run
  only in the fuzz. `against_original` compares main RAM, not the scratchpad, so the tests copy
  the scratchpad's drawing state (the projected points, the segments' tops) into free RAM after
  each run, with the GTE's registers. The set-up runs while the race loads, and there `fixedsin`
  and `fixedcos` tick once each: their `fastintcos` runs on into `fastintsin`, which recompiled
  code reaches by a continuation (`run_cont`, a tick). The ports use `fixed::fixedsin_ticked`
  and `fixedcos_ticked`.

- **The spin-tick trap.** The recompiled code ticks the CPU at each backward branch it takes,
  and `Cpu::call` (a call by address: a `jalr`, a hooked or host-replaced function) ticks once
  and goes through the host, which restarts its count; after 20,000 ticks without a call to it
  the host takes the game for spinning on a busy-wait and moves its clock on a tick. Race frames
  stay far from that (measured with `PS1_SPINSTAT=1`: about 5,100 at most), but loading doesn't
  (67,230 at a race's start), so a port that runs while the game loads must tick exactly as its
  original does, and call as it does: `call::call_jal` is the original's `jal` (the port if
  there is one, else the recompiled code directly, the host only for the functions it hooks or
  replaces), `call::call_addr` a `jalr` (always through the host), `call::ticks` the loops'
  passes. Found twice: the replay buffer's clear, then night driving with police (millions of
  colour searches at the load; the race's clocks two ticks behind from the first frame).
  `test_util::COMPARE_TICKS` makes the fuzz compare the ticks each run takes, which caught every
  missing tick (a library call like `memset` replaced by plain Rust is one). The older readable
  ports (the front end, the HUD, the camera, the pause menu) call by `call_addr` and don't tick
  their loops; the bit-exact ports don't tick either (`BWorldSm_FindClosestQuadRez`'s road
  search is why `Fog_Update`'s ticks aren't compared). None of them has diverged a tour or race
  yet; moving them over is a separate step.

- **Calling a port.** Routing happens at the recompiled call sites: a port calling another
  function's recompiled original (`nfs4rc::f_*`) runs the original even once that function is
  decompiled. Until 2026-11-03, 112 calls did (the race loop's camera and AI start-up and
  clean-up, the HUD's views and their parts, the AI's HUD notices, the front end's fades): the
  ports never ran from there, and the checks compared the original with itself. They go by
  address now (`call_addr`, `Saved::call_ptr`; readable to readable as plain Rust where no hook
  cares), and `tools/hookaudit.py` reports any such call.

## Checking

- **Unit tests** (`cargo test -p nfs4 --release`: in release, since fuzzed pointers and counts trip a debug build's overflow checks where the original wraps) compare pure functions with their recompiled
  originals on a bare CPU, over edge cases and random inputs (they need `gamedata/NFS4.EXE`
  for its tables). **Fuzz tests** do the same for whole functions on a real race's RAM
  (`re/boot/ram.bin`, written by `BOOT_RAM=1 nfshs boot-race`), the player's car perturbed
  into states races rarely reach: road-side control, upside down, at the barriers, every
  setup. Test CPUs need the game's `gp` (0x8013D83C): its small globals are gp-relative.
- **Shadow checks**: `NFSHS_DECOMP_CHECK=all` (or a list of names; add `abort` to stop at
  the first mismatch). Every call of a checked function from recompiled code runs the
  original first from a copy of the machine, then the Rust version from the same state, and
  compares RAM, the scratchpad, the callee-saved registers and v0. The dead stack below the
  caller's is left out; in a race the stack is in the scratchpad. A mismatch is reported by
  field (`car[0].N.linearVel.y`). Checks don't nest: to check a function that decompiled
  code calls, run its callers recompiled with `NFSHS_DECOMP_ONLY=Name,...`.
  `NFSHS_DECOMP_STATS=1` prints the calls, checks and mismatches per function.
- **The test CPUs** have no host: a call to a library function the recompiled code doesn't
  have (from 0x800e0000 on: the pads, VSync, CD the host answers) or through a null pointer
  returns 0 (`PadGetState` a stable pad), in the original's run and the port's alike; code
  below that isn't recompiled (jumps into functions) is interpreted as usual. Code that
  waits on the hardware (resetting the HUD, the track's drawing) can't run there; whole races
  check it. `same_stack` gives both runs the same `rand()` seed and compares it after.
